A production adapter/configuration and delivery-failure policy must be deliberately designed and tested. Merely changing SMTP settings or deleting local guards is insufficient. Hosted student assisted reset remains disabled by local recovery guards. Enabling it requires its own operational/private-handover/abuse/retention acceptance, not an environment-variable toggle. Member IDs remain stable; no mandatory student phone/email or self-service contact replacement is introduced.

The composed pilot creates fictional staff scopes and offering/cohort setup through its harness. It does not prove complete real offering/cohort or staff-grant provisioning interfaces. L1 must identify the supported authorised operational path and any missing tooling before onboarding; never run a fixture bootstrap or improvise broad database grants against real users. Content ownership/import review also remains necessary; linked teaching sheets are not automatically imported or approval to copy personal data. Website intake, payments and other deferred modules are not launch dependencies unless the owner includes them explicitly in the first release scope.

Current service-only purge functions and fictional notification Cron do not establish production ownership or complete scheduled Storage cleanup. Inventory each object's references/holds/expiry and delete through the supported Storage API, not just SQL metadata deletion. Never use a replacement account's authority for compensation.

## Backups and recovery targets

Supabase database backups omit Storage file bytes. Keep a separate approved object-backup strategy and consistent manifest alongside database recovery; verify a restored file actually opens. Pro daily DB backup retention is seven days, not indefinite recovery. [Backup scope](https://supabase.com/docs/guides/platform/backups), [plan details](https://supabase.com/pricing).

Proposed discussion targets, **not promises or accepted policy**: at most 24 hours of data loss (RPO) and restoration within four hours (RTO). Daily database backup alone does not establish either target for files or Auth. Measure a full fictional restore before accepting targets; tighter targets may require different architecture/spending. Encrypted backup access, key recovery, off-project custody, retention and deletion handling need named owners and approval. Never put dumps, credentials, action links, MFA seeds or file contents into GitHub, screenshots or tickets.

Restore in isolation with sending/jobs disabled. Reapply current erasure tombstones/retention and validate grants/session invalidation before opening access; an old backup must not resurrect access or deleted data. Maintain configuration/secrets recovery separately and use supported Auth/Storage procedures; no direct edits to provider-owned Auth tables or blind restore to the live project. Application rollback is not database/file rollback, and a staging rebuild is not a backup drill.

## Capacity assumptions and cheaper scaling

Owner-confirmed planning input (2026-10-15): **up to 50 students in the first three months**. Use 50 as the initial capacity/budget planning ceiling, not permission to onboard real students. Submission frequency, file sizes, concurrency and subsequent cohort growth remain illustrative until measured or confirmed.

Example: 50 students × 8 submissions/month × 4 MB total per submission = 1.6 GB/month; 1 MB voice feedback per submission adds 0.4 GB/month. One fixed 50-student cohort submitting for six months produces about 12 GB, retained through its existing post-course window; it does **not** keep submitting after course end. If successive cohorts instead maintain 50 active students and accumulate 18 months of work before the first cohort's purge, the illustration becomes roughly 36 GB. At 200 continuously active students with the same rolling-cohort pattern, that is 144 GB and cannot be assumed to fit the 100 GB included file quota. These figures exclude revisions, lesson files, database data and separate backup copies. This is not a retention change; access expiry and physical cleanup follow existing approved policies/holds. Compression already exists for eligible student images; PDFs, revisions and actual file behaviour must be measured.

Three combined student/teacher downloads of each submission add roughly 4.8 GB/month at the 50-student illustration, excluding other traffic and backup exports. Measure actual workload, not just MAU limits. Before launch, test a bounded synthetic peak of simultaneous sign-ins, lesson reads, uploads, reviews and worker catch-up; record latency/errors, query cost, disk/egress growth and quota response. Set numerical pass/fail targets only with the bounded workload, not arbitrary user-count guarantees. Preserve portable PostgreSQL migrations and provider-neutral interfaces; don't introduce video, a second storage vendor, self-hosting or microservices just to chase headline free quotas.
