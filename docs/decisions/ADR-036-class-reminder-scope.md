## Question

Should active students receive advance reminders for scheduled classes?

## Why this needs your decision

F021 sends schedule/change/cancellation alerts; F022 now delivers existing in-app events automatically. Neither approves a new reminder default, timing or preference. The next slice changes student communication behavior.

## Options

### A — Defer advance reminders

Keep current schedule/change/cancellation alerts only. No extra vendor spend or reminder implementation. Reversible later; students must consult their agenda.

### B — Optional single in-app reminder (recommended)

Students explicitly opt in to one reminder 24 hours before each class. Default off. Only current active offering/cohort members receive it; rescheduling/cancellation invalidates obsolete work. Opt-out and course closeout stop future reminders. No late catch-up after the class starts, external delivery, custom timing, staff override or teacher authority. Notifications use existing bounded retention and generic safe content. A separate user-controlled setting is needed; no passive analytics. Existing stack, no additional vendor spend for fictional testing; not a production approval or guarantee of instant delivery/uptime.

### C — Discover a broader reminder policy first

Define configurable timing, quiet hours, preferences and possible external channels before implementation. Discovery adds no vendor spend; actual email/SMS/WhatsApp/push requires separate provider/privacy/cost approval. Larger scope and more decisions; no messages sent meanwhile.

## Recommendation

B adds useful advance notice without forced messages or a new vendor. The opt-in and policy can be changed later, preserving immutable delivery history while invalidating obsolete pending work.

## What can continue while pending

Existing approved alerts and fictional native worker remain operational. No reminder jobs or new student preference is implemented until selection.
